# Classic RACG challenge workflow

Use this skill only when generating a new randomized challenge or publishing/revising one. **Before writing ANY new solver-facing statement**, read `references/contest_problem_design.md` (CodeChef corpus lessons and the RACG-0040 ACCEPT/REJECT rewrite) AND `references/specification_comprehension.md` (the exact six-level reader rules). Read `references/racg.md` and `references/ards2_workflow.md` for the draw and release contracts. Use `website/PROBLEM_AUTHORING_STANDARD.md` for browser-visible statements.

## Preserve authentic randomness and provenance

- Retrieve current state from `data/ards.db` before drawing. `python3 scripts/racg.py --status` inspects single-draw state. **For requests to author multiple challenges, first read `references/batch_authoring.md` and use `python3 scripts/ards_batch.py status`, then `create --count N` exactly once if needed.**
- For a new challenge call the actual generator once. Persist independently drawn O, Y, P; draw X only on the fresh-topic branch. Record the actual continuation decision, topic ID, difficulty, presentation style, and any verification-specific Z pattern planning. Do not fabricate or reroll.
- Classic RACG v1.2 uses weighted Levels 1–6 (30%, 25%, 20%, 12%, 8%, 5%), without a mastery gate. For continuations, renormalize the weights of eligible levels instead of clamping; `references/racg.md` defines the exact draw protocol. Respect the saved story/direct presentation draw. Direct challenges use precise, non-narrative definitions; story challenges may use natural context.
- Include a factual generation report based on stored metadata; don't disclose technique-identifying topic labels before an independent attempt when doing so would leak hints.
- In a batch, continuation extends the previous queued selection even if that selection is not yet publicly released. The batch draws and reasoning plans are stored atomically, so one unsupported verification family never blocks reserving the other slots. Do not use the single-draw command to bypass a queued challenge.

## Build and release a problem

1. Search the archive for near duplicates; investigate candidates without changing saved draws.
2. **First design a distinct reasoning challenge, then present it as an independent contest question.** Follow BOTH `references/contest_problem_design.md` and the SIX worked profiles in `references/specification_comprehension.md` for the exact saved level; do not improvise a generic low/high rule. The saved topic/pattern informs the private problem model but does not need to be named in public, and a difficult algorithm should not require cryptic reading. For Level 1–3 students, define all non-everyday objects, operations and relationships without prerequisite knowledge of the topic; Levels 4–6 may require mathematical interpretation but never incomplete rules. **Write the description before its input syntax**: introduce the objects, initial state, what each allowed action or condition means, changes across operations, and the exact question, including failure/tie/empty cases. Only THEN give the input codes and line format. **RACG-0040 is the required comparison:** reject its compressed `1 i d`/`2 K 0` one-paragraph explanation; accept the worked rewrite which defines the tokens, consecutive bins, updates, timing and exceptions in natural language before encoding. Honor the real story/direct draw: stories must encode meaningful rules, not cosmetic data-structure aliases; direct text must be equally complete. Do not expose Fenwick trees, algorithm names, formulas that give away the insight, or solver pseudocode. Select an original objective with genuine conceptual variety (optimization, possibilities, feasibility, construction, transformation, inference, counting, etc.) rather than repeatedly reskinning update/query exercises. For NEW problems, use ordinary contest stdin/stdout, realistic natural token layouts, no artificial trailing padding values, and no leading T without multiple test cases. Record exact constraints, samples and model semantics; do not silently change input contracts of released challenges.
3. Create a complete, **teacher-only, typeset Markdown + KaTeX** reference PPC with `problem` (P1), `procedure` (P2), `correctness` (C), and `complexity` (K) **before registering the problem**. **Presentation is mandatory:** use `\(...\)` for inline math and `\[...\]` for centered display equations, not ASCII `<=`, bare `a^2+b^2`, or long unbroken prose. Organize correctness as a readable theorem/claim, appropriately named proof steps, termination and conclusion, with separate paragraphs and display formulas for crucial equations. Inspect the rendered PPC before releasing; do not use a one-paragraph proof dump. Follow `references/ppc_authoring_style.md`, including its **worked Level 1 Ticket Window P1/C example** and the six learner PPC examples. P1 must define the full valid input domain, precise output relation, constraints, and applicable boundary/feasibility/optimization conventions; do not replace it with a one-line array slice or answer slogan. C must state an explicit claim for **every valid input**, establish the actual P2 procedure satisfies **every P1 obligation**, justify the chosen proof method and logical steps, cover necessary/sufficient directions and optimality if relevant, and establish termination and boundaries. Build a P1-to-C proof-obligation mapping privately during authoring; correct missing obligations before registration. **All six levels demand the same rigor**, though the suitable proof technique and length vary; do not force an invariant or boilerplate. This authoring self-audit is separate from and cannot replace the mandatory independent `ppc_review` for queued releases (see `references/independent_review.md`). Never include reference PPC in a student statement, preview, or public endpoint. Test/structure evidence does not itself prove mathematical correctness.
4. **Run both public-statement audits before registration:** (a) the exact six-level comprehension test, and (b) the CodeChef-inspired design/reasoning checklist and RACG-0040 counterexample in `references/contest_problem_design.md`. A reader of the description **without first parsing the command codes** must identify the objects, legal operations, their timing, the question, and what makes an answer valid; a solver should still have to discover the algorithm. Reject an operation-code-only summary, artificial story padding, a renamed previous challenge, or hidden solution hints. Then validate the public format using `python3 website/validate_display.py PACKAGE.json` and independently verify samples and edge behavior with the relevant oracle.
5. Use `scripts/ards2.py` and its documented verification-gated release path. For queued batch challenges, first-party `test_verified` alone cannot authorize release; require matching independent review evidence and database-validated plain-text stdin/stdout. For generated batch problems, separately read `references/independent_review.md`; provide a truly separate executable reviewer candidate, independent brute/exhaustive oracle, edge/random/sample checks, and substantive written review before an incremental release. A structure check or passing test suite is not a universal mathematical proof. **For a multi-problem request, register each full problem with its PPC, mark unsupported/failed items `under_review`, then proceed to author the next item instead of stopping the batch.**
6. Check the persisted release, **rendered student-view description against the RACG-0040 worked acceptance example**, spoiler isolation, and unchanged historical attempts. Before release, append corrections with `scripts/ards2.py revise-draft` and reverify the new package hash; after release use the versioned `amend` path. Never overwrite a previous draft.
